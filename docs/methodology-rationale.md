# Methodology Rationale

This repo demonstrates a generalist path for enterprise domain adaptation with
LoRA. The NIM and NeMo Microservices corpora are representative public
examples, not the boundary of the method. The same pattern applies to any scoped enterprise domain or
sub-domain where the source material is specific, valuable, and small enough
that generic web-scale training has not made the target behavior obvious to a
base model.

## Why Nemotron 3 Super For LE Extraction

Stage 1A defaults to Nemotron 3 Super 120B-equivalent generation for logical
entailment (LE) extraction and QA/KVP conversion. That is intentional.

LE extraction is a high-recall transformation task: each passage is converted
into explicit premises, conclusions, and grounded question-answer pairs. The
model must preserve source boundaries, avoid unsupported interpolation, and
produce structured output that downstream stages can validate and resume. A
small model can run cheaply, but it is more likely to miss latent premises,
flatten conditional logic, or produce brittle JSON. A much larger frontier model
can be useful for targeted audit, synthesis, or difficult edge cases, but it is
not always the right default for full-corpus extraction.

Nemotron 3 Super provides the middle ground used by the case study: strong
instruction following and reasoning capacity, practical throughput through NIM
or OpenAI-compatible inference, and enough quality to run the full Stage 1A corpus
without making extraction cost dominate the experiment. In this repo,
`nvidia/nemotron-3-super-v3` and
`nvidia/nemotron-3-super-120b-a12b` are treated as exact-equivalent model IDs
for the documented runs.

## Why Compare Several Dense Sizes

The evaluation matrix intentionally spans dense Llama-family targets across
1B, 3B, and 8B LoRA adapters, with Llama 3.3 70B as a no-adapter dense
reference target. The purpose is downselection, not spectacle.

Single-axis scoring estimates standalone answer quality for each trained
adapter. Pairwise scoring then compares only the strongest LoRA candidates in
each size class against the 70B reference. This shows whether the dataset
generation method creates useful domain specificity, whether the adapter rank
matters, and where a smaller dense model stops being sufficient. A 1B adapter
may be enough for narrow terminology and routine answers; a 3B or 8B adapter
may be needed when the corpus requires more synthesis; and the 70B reference
anchors the result against a strong dense model that has no domain adapter.

The value of the matrix is operational. It helps a team choose the smallest
model that meets the target quality bar for its domain, latency, and serving
cost, while preserving evidence about why larger or smaller options were not
selected.

## Why LE Is Relevant To NeMo RL

The LE path captures more than plain QA text. It preserves the source passage,
the extracted premise, the inferred conclusion, provenance, and the generated
question-answer pair. That structure is useful beyond SFT.

For a future NeMo RL or RLHF/RLAIF-style workflow, the LE record can become the
basis for reward and preference data. Positive examples are answers that follow
from the recorded premises and conclusion. Negative or contrastive examples can
be generated by omitting a required premise, contradicting the conclusion,
answering from outside the source, or overgeneralizing beyond the passage. The
judge or reward model can then score whether the response respects the logical
support chain, not merely whether it resembles an answer string.

This is not presented as a formal theorem prover. The point is practical:
Aristotelian-style reasoning structure - premises supporting a conclusion -
creates inspectable supervision. That makes the data easier to audit, easier to
turn into preference comparisons, and better aligned with reinforcement
learning objectives that reward grounded, logically supported answers.

## Why LE Complements Curator Instead Of Replacing It

The LE approach exists because many enterprise domains have small, specific
corpora: internal procedures, field manuals, policy collections, support
playbooks, architecture runbooks, research protocols, or other scoped domain
materials. In
that setting, the highest-value signal may be the precise local reasoning and
nomenclature encoded in a few hundred or a few thousand source passages. LE
turns that limited source material into grounded, auditable training rows with
explicit provenance.

NeMo Curator remains fundamental. Curator is better suited for massive scale,
high-throughput filtering, deduplication, document preparation, synthetic data
workflows, and full SFT data preparation where the objective is to adapt model
weights over a broad distribution. This repo uses Curator where it is strongest:
quality filtering, deduplication, length/token controls, dataset finalization,
and optional DiverseQA/Data Designer paths.

The comparison in this repo is therefore not "LE versus Curator" as a universal
replacement argument. It is a case-study question: for small corpus-specific
LoRA adaptation, how does an LE-generated dataset compare with a Curator
DiverseQA dataset on the same corpora, under matched training and evaluation
conditions? The pipeline keeps both paths available because the
right choice depends on corpus size, quality target, budget, and whether the
desired outcome is a lightweight domain adapter or a larger full-SFT effort.
